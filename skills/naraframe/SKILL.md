# NaraFrame

Operate NaraFrame through its public CLI and authoritative project files. Keep the pinned profile in control of creative decisions and treat structured command results as the authority for readiness, repair, and resume decisions.

## Workflow

Choose the engine invocation before authoring. If this skill folder has `installation.json`, read it and use `node "<this-skill-folder>/scripts/naraframe.mjs"` from the episode's working directory. The launcher verifies the recorded engine/version before forwarding argv; engine resources such as `library/` and `starter/` live under the receipt's absolute `resourceRoot`. It does not modify PATH or host permissions. Read [installation.md](installation.md) for install/update and troubleshooting.

For an uninstalled source checkout, run from its root with `pnpm naraframe`. Activate its pinned Node and pnpm versions in `.node-version` and `packageManager`; installed engine use needs the pinned Node/runtime tools, not a pnpm development checkout. If the runtime is unavailable, report a system blocker; do not rewrite dependencies. In every guide below, substitute the selected invocation for `pnpm naraframe` and resolve bundled catalog/example paths from `resourceRoot` or the skill folder, not the episode's cwd.

1. Run `pnpm naraframe doctor --json`. Resolve every structured system issue before previewing; `doctor` performs no download or render.
2. Run `pnpm naraframe schema --json` and use the returned schemas when creating or repairing source. Save the large result to a local file and inspect the relevant schema/capability entries rather than repeatedly loading the entire output into context. Do not reproduce schema definitions in this skill.
3. Establish the project and profile before creative edits:
   - New project: run `pnpm naraframe create <project> --profile <id-or-path> --json`, then read the created `profile.lock.json`, including its pinned direction text.
   - Existing project: run `pnpm naraframe status <project> --json`, then read that project's `profile.lock.json` before revising it.
4. Write a short rundown in each scene's `note` before choosing effects: **takeaway → explanatory object and parts → framing → type hierarchy → beat jobs and pace → incoming/outgoing focus**. Map the narration's cause, change or relation to something the viewer can point at (a note, route, quantity or place). Use independent parts for independent movement. Keep one dominant statement, then supporting labels; emphasize the turning phrase with role/spans so the profile owns its appearance. Specify what each motion explains and where it settles. Give the viewer time to read after the change. Read [art-direction.md](art-direction.md) for six editable patterns and their public paths, knobs, dependencies and limits; runnable source is [examples/art-direction/scenes.json](examples/art-direction/scenes.json). These are choices, not a universal shot template.

   Revise inside this brief yourself. Ask the user about the story and the facts, not about pixel values.
5. For recurring episodes or supplied catalog art, read [library.md](library.md) and inspect suitable patterns before recreating the structure. Pin a version through `library stage` → ordinary `edit`; local instances remain editable and catalog updates are explicit. Edit only authoritative source such as `naraframe.json`, `scenes.json`, and `assets/manifest.json`, following the returned schema and pinned profile direction. Prefer bounded `stack`/`grid` groups for repeated content, declare text limits and avoidance targets, and declare image crop, focal point, radius, stroke, and shadow when profile defaults are insufficient. Never edit generated preview files.
6. Run `pnpm naraframe validate <project> --stage plan --json` after every source edit and before every preview. Use each issue's `code`, `responsible`, `artifact`, `path`, `message`, and `suggestion` to decide who should repair what; validate again after repairs. It catches compile-time problems without rendering: schema and reference errors, timing windows, static layer bounds, counts and phrase anchors. Visual preflight (text overflow and collisions, text leaving the screen under camera, object or scene-transition motion, text whose motion carries it out of the safe zone as a `TEXT_OUTSIDE_SAFE_ZONE` warning, font loading, masks) runs only in `preview`, so a valid plan can still fail there.
7. Only when validation reports no errors, run `pnpm naraframe preview <project> --draft --json`, optionally adding `--scene <scene-id>` for a short local check. Treat any visual-preflight issue as a source/profile repair, not a renderer override.
8. Preserve the first successful draft MP4, contact sheet and source before feedback, then inspect the exact paths in the successful result's `artifacts`. Review scene entry, settled, beat peak, transition/final states, and any requested editorial timestamps; check masks during motion, hierarchy, overflow, collisions, and whether the object explains the takeaway. Metadata alone is not visual acceptance. Record reads/help, correction count, elapsed time, reuse and provider use; unknown cost or active time stays unknown. Keep owner visual acceptance separate from technical readiness.
9. Run `pnpm naraframe status <project> --json` to resume or verify. Continue only from its authoritative current build and reported artifacts. A stale preview must be rebuilt and inspected.
10. For revisions, reread the pinned profile and use ordinary `edit` revisions, then repeat validation, preview inspection, and status verification. “Make the point clearer” changes headline/hierarchy/object; “give it breathing room” changes beat/camera start and duration plus the settled hold. Shorten/reflow copy or change layout bounds before reducing text below the profile minimum. Plan at most two internal correction passes per checkpoint, retain failed attempts and report remaining issues.

## Production vocabulary

For an existing voice take, supplied timing or reusable series identity, read [prepared-audio.md](prepared-audio.md). Import captured audio through `audio stage` → guarded `edit`; distinguish pending alignment from a real listening attestation. Never regenerate an accepted master to revise visuals.

For caption policy or styling revisions, read [captions.md](captions.md). Keep caption display separate from the narration: none/selected/full controls the visible cues, not the voice. Follow the pinned profile's caption defaults and locks, and inspect cue boundaries at the intended output resolution.

Choose a beat by its job: **reveal** introduces a part; **trace** draws a relation; **compare** aligns like quantities; **reframe** changes what the camera lets the viewer understand; **emphasize** returns attention to the turning point; **hold** leaves the composition still. These words describe existing beats/camera or no motion, not new actions in JSON. Alternate pace according to the story, not a quota. Preserve an outgoing focus point or reading direction into the next shot when continuity helps. An explicit neutral `cut` is a valid change of thought; a missed transition is an unintended jump or lost focus revealed by inspecting both sides. Profile variety warnings are profile guidance; quiet shots and cuts can be deliberate.

## Space, camera and timing

Read this before authoring a camera, world layers or motion; `schema --json` gives the fields, this gives what they do.

**Coordinates.** Author every frame, point and camera offset in the project's design canvas, `format.design` in `naraframe.json` (width W, height H); drafts scale all of them to `format.draft`. C = (W/2, H/2) is the canvas centre.

**Overlay and world.** A layer is overlay unless it or its group says `space: "world"`; grouped layers take their group's plane. A group without a `frame` keeps its members' own frames; members' `zIndex` orders them inside the group, and the group's `zIndex` places the whole group among other layers. Overlay is fixed to the screen, ignores the camera and must fit the canvas (`LAYER_OUTSIDE_CANVAS`). World layers move with the scene `camera`: with depth d = `parallax` (default 1, 0 to 2) and camera pose (x, y, zoom), a world point P lands on screen at

    screen = C + zoom^d · (P − C) − d · (x, y)

So camera (0, 0, 1) shows world coordinates as screen coordinates, d = 1 is the main plane, d < 1 moves and zooms less (far), d > 1 more (near), and d = 0 never moves. World images and shapes may extend past the canvas; world text may only in a scene with a camera, where preflight checks it on screen frame by frame.

**Camera.** `camera.initial` plus `moves`, each starting from the pose the previous one reached. Moves must not overlap (`CAMERA_MOVE_OVERLAP`) or end after the scene; zoom is 0.25 to 4. Easing presets: `linear`, `smooth` (ease in and out), `snappy` (ease out; the default for camera moves and most beats). Within a move, x, y and zoom share one eased progress and each is interpolated linearly between the two poses (zoom too, not geometrically).

**Framing recipe.** Draw world plates at the pose where the shot settles, so that pose is camera (0, 0, 1). To centre a depth-1 point Q at zoom z, use x = z · (Q.x − C.x), y = z · (Q.y − C.y). Extend plates far enough for every pose the camera passes through, remembering the zoom: on the main plane the visible area moves steadily between two poses, so covering both end poses is enough; for other depths also check the pose halfway.

**Billboards.** A world group with `billboard: {x, y}` rides its plane at that world point but keeps its design size, so a map or street label stays readable while the camera zooms. Its members keep ordinary design-canvas frames, placed around that point where they should sit when the camera is at (0, 0, 1); the group moves them with the point without scaling them.

**Poses.** `transform` values are a pose, not a delta: offsets x and y from the layer's frame, scale and rotation. Before any beat moves a layer its pose is x 0, y 0, scale 1, rotation 0, and each `transform` eases the properties it names from the current pose to its values. A `follow` is different: while it runs, the layer's centre sits on the path point for that moment (turned to face its travel with `orient`), whatever pose came before. If the first beat that moves a layer is a `follow`, the layer already waits at that follow's `from` point before its window. A later `follow` does not blend in from the previous pose: the layer jumps to the path unless the preceding pose already puts its centre on the path's `from` point, so align those endpoints (or start the path where the object is) for a continuous move. A `transform` after a `follow` eases from where the follow left the layer. To pop something in from a scaled or offset state, transform to that state over one frame while it is still hidden, then reveal it and transform back. A `reveal` keeps its target hidden until its window and enters from `distance` in `direction` (distance 0 only fades). An `exit` fades out, optionally drifting, and leaves its target hidden for the rest of the scene. The scene id may be the target of reveal, exit, emphasize or focus, never transform.

**Timing in frames.** A beat starts at frame round(startMs · fps / 1000) and lasts max(1, round(durationMs · fps / 1000)) frames, up to but not including its end frame; with narration, `at` resolves first, and the scene's length comes from its phrases. Writes to one target property by `transform`, `exit`, `draw`, `follow` or `count` must not overlap after this rounding (`MOTION_PROPERTY_OVERLAP`), and every beat must end inside its scene (`BEAT_OUTSIDE_SCENE`). Their messages give the frames involved and a start or duration that clears the problem; apply it and validate again. Steps shorter than about two frames need a frame of margin (at 30 fps, 60 ms nudges spaced 67 ms apart, not 60).

## Claims and sources

The engine never detects claims; it trusts the labels you write. A factual claim is a statement about the world presented as true: a cause, quantity, date, place, or named person or event. Questions, instructions, opinions marked as such and on-screen labels are not claims. Decide per scene and per narration block, from the words the viewer reads or hears, and ask the user about facts you cannot verify.

- Label each claim with `carriesFactualClaim: true` on the scene in `scenes.json` or the block in `narration.json`. Leave it `false` only when nothing is claimed; do not copy `false` from an example. Say why in the scene `note`.
- Declare each source once under `sources` (`id`, `title`, optional `url` and `retrievedAt`) in either file, then cite it from `sourceIds`. Ids are unique across both files; a cited id that is not declared is `SOURCE_UNKNOWN`.
- A labelled claim without a source is a `SOURCE_MISSING` warning, and an error when the profile sets `requireSourcing` (`validate`, `preview` and `render` then stop). If a claim is restated without a source, record the owner's decision in the project notes; do not relabel it `false` to pass.
- When `requireSourcing` is set and nothing is labelled, `validate` reports one info issue, `CLAIMS_UNLABELLED`. It never blocks. Reread every scene and block, then either label and source the claims or tell the user the episode makes none.

## Boundaries

- Treat one newline-terminated `CommandResultEvent` on stdout as the machine result; diagnostics and progress on stderr are not the result.
- Stop on `success: false`. Repair agent-responsible source issues, ask the user for user-responsible choices, and surface system-responsible dependency issues.
- Never import private package modules, write `.naraframe/compiled.json`, write preview metadata, or invent identifiers absent from the result.
- A `preview` is a labelled `DRAFT` review build. Only `render` with an approval (below) produces a final, and a final is not a publication: never call output published or publish-ready.
- Call only `version`, `doctor`, `schema`, `create`, `validate --stage plan`, `status`, `validate --stage production [--scene <id>]`, `recipe trust` (only as described below), `preview` (with or without `--draft`, optionally `--scene <id>` and `--resolution 540|1080`), `edit`, `undo`, `render`, `cache clean`, `profile inspect|apply`, `library inspect|stage` (as described in [library.md](library.md)), and `audio stage` (as described in [prepared-audio.md](prepared-audio.md)); do not advertise or guess future commands.
- Prefer `edit` over rewriting files in place when a change should be reviewable or undoable: put only the changed source files in a staging directory laid out like the project, read the current revision from `status` (`sourceRevision`), then run `pnpm naraframe edit <project> --from <staging-dir> --expect <sourceRevision> --summary "<what changed>" --json`. `REVISION_CONFLICT` means the project moved on: re-read `status`, re-apply the change, retry. The result carries `data.reuse`: how much of the previous revision's voice, images, and scenes survived, and the recorded cost against a full regeneration (unknown or untracked spend stays visible and is never guessed). To delete an optional source file in the same revision add `--remove narration.json` and/or `--remove captions.json` (repeatable, no other file is accepted; `--from` becomes optional when only removing): `REMOVE_NOT_ALLOWED` names a required or unknown file, `REMOVE_TARGET_ABSENT` a file the project does not have. `undo` restores the previous accepted revision, including a removed file, without any provider call; receipts and spend are never rolled back.
- A final export needs `validate --stage production` to pass and one approval. Run a full `preview` that carries the project's audio (narration, music or none for silent), have the owner review it, then `pnpm naraframe render <project> --approve-preview <build-id> --json`. Use `--autonomous --authorized-by <name>` only when the owner has said in chat that you may export without reviewing a preview; never add it on your own initiative. An approval covers one source revision: after any edit, review a new preview. Report the export from `artifacts.finalMp4` and do not call it published.
- Set the audio mode the brief asks for in `naraframe.json` as `audioMode`: `"voice"` (narration, optionally with a music bed), `"music"` (a music bed, no speech) or `"silent"` (no audio stream). A profile may default it under `production.audioMode` and may lock it. `validate --stage production`, `preview` and `render` report the resolved mode as `data.audioMode` with its source (`project`, `profile` or `legacy`); tell the owner which mode applies. Music-only and silent projects use the scenes' `durationMs` as the final clock and reach a native 1080×1920 final through the same preview-approval-render route. Never add empty or silent narration to get past a check. To make a voiced project silent, stage `naraframe.json` with `audioMode: "silent"` and run `edit --from STAGING --remove narration.json --expect REVISION` (never delete `narration.json` by hand); if `captions.json` selects narration phrases, validation names `CAPTION_SELECTION_TARGET_UNKNOWN`: add `--remove captions.json` or stage a `captions.json` with mode `none`. `AUDIO_MODE_UNDECLARED` means a project without narration has not declared its mode, so its durations are still draft timing: declare it after the owner confirms the timing. `NARRATION_REQUIRED` means voice was requested but narration is missing; do not switch to music by yourself. `MUSIC_REQUIRED` names a missing music bed at export. `AUDIO_MODE_CONFLICT` (narration under a non-voice mode, or a soundtrack in a silent project) and `AUDIO_MODE_LOCKED` (a mode the profile locks differently) are source errors: every preview refuses them before rendering, `--draft` included, while missing narration, music or a mode declaration only block the final export.
- Know which route a project is on. **Draft without a declared mode**: no `narration.json` and no `audioMode`; previews are labelled `DRAFT • NO AUDIO` or `DRAFT • WITH AUDIO` (music), and `render` refuses it with `AUDIO_MODE_UNDECLARED`. **Prepared media**: import an existing take and local timing through `audio stage` → `edit` using [prepared-audio.md](prepared-audio.md). A pending receipt permits draft review but blocks production; verified listening records bind the captured audio, text and cues. Existing ready blocks without that receipt retain their legacy path. **Generated**: calling a voice provider from NaraFrame is not available through the CLI yet; every real paid call needs the owner's authorisation and a receipt in `production.json`, so never spend or call a provider on your own.
- To check or review one scene while others are unfinished, use `--scene <id>`: `validate --stage production --scene <id>` and `preview --scene <id>` (no `--draft`) require only that scene and its dependencies to be ready, and list other scenes' gaps as `info`. A final `render` still needs everything. A preview of a scene starts at time zero; its global position may be unknown (null) until earlier blocks have audio.
- Previews default to 540×960. Use `preview --resolution 1080` when the owner needs to judge crop, line wrapping or small type at final size: it renders natively at 1080×1920 (still labelled DRAFT), has its own build keys, and a full 1080 preview of the current source can be approved for `render`. More pixels do not add detail a small source image lacks; say so instead of implying sharper media.
- After a change that cannot alter pixels, such as a scene `note`, `preview` reuses the earlier build's pixels and reports `reusedFromBuildId`; you still need a fresh review and approval for the new revision. Use `--rerender` only when you need a real render.
- `profile inspect <id-or-path>` shows a profile without a project. `profile apply <id-or-path> [project] --dry-run` lists changes, effects (recompile, revalidate-layout, regenerate-narration only when the project has narration, replace-assets, editorial-review), kept overrides and conflicts without touching anything. When the palette, direction or illustration style changes, `plan.review` also names the scene content to look at: `paletteBound` (layers painted from a palette slot with its before and after colour), `literalColors` (hex colours the switch will not repaint) and `imageLayers` (scene, layer and asset); it reads `scenes.json` only, so preview the affected scenes before telling the owner the switch is done. A plain `apply` commits one revision and `undo` restores the old profile. An override the new profile locks or no longer allows blocks apply; `--reset-overrides` drops it explicitly and undo brings it back.
- **Brand-managed profiles** carry a `brand` block (`name`, `audience`, `editorial` notes, `cta {label, url}`), PNG assets with a `role` (`logo`, `person`, `product`, `illustration`, `background`) and may default `production.audioMode`; `profile inspect` shows them. Choose the profile first, read its editorial notes, and keep episode facts and copy in the project. In a brand-managed project every used image or vector needs a `binding` in `assets/manifest.json`: `"neutral"` when any brand may use it, or `{"brand": "<profile id>", "role": "..."}` when it carries that brand's identity (logo, the brand's own people). Text that must show the brand's name or call to action carries `"binding": "brand.name" | "brand.cta.label" | "brand.cta.url"` and the same text as the profile. Drafts only warn; `validate --stage production` and `render` refuse `ASSET_BINDING_UNKNOWN`, `BRAND_ASSET_MISMATCH`, `BRAND_TEXT_MISMATCH` and `BRAND_FIELD_MISSING`, and report the resolved brand under `data.brand`. Before switching brands run `profile apply <profile> <project> --dry-run`: `plan.bindings` lists `compatible` assets already bound to the target brand, `branded` assets with the new profile's replacement for their role, `incompatible` ones it cannot replace, `neutral` (only those marked `"neutral"`), `unknown`, bound text with its new value, and scenes with factual `claims`. A switch never rewrites copy or claims and never makes another brand's photo acceptable: show the owner the list, then change content through `edit`.
- After a profile change the draft still compiles. Voice made with the old style shows in `status` under `needsProduction`; final export waits until it is regenerated.
- After a profile change, or any change whose dry-run lists `revalidate-layout`, check layout straight away. `validate --stage plan` catches geometry it can compute, including image mask radii from the profile's defaults (`IMAGE_MASK_INVALID`), but text size is measured only in `preview`. So run `preview --draft` (or `--scene <id>` per affected scene) as the layout check: a preview whose preflight fails is rejected in seconds, before any frame is rendered, and lists every measurable problem at once. Repair them all in one pass. Expect one more round when `TEXT_OVERFLOW` or `MIN_FONT_SIZE_VIOLATION` was reported: a layer's collision and off-canvas checks run only once it fits. Keep neighbouring text boxes from touching, so a larger face cannot turn a hidden overlap into a collision, and look at every `CONTRAST_UNVERIFIED` text in the frames. Box sizes in preflight messages are draft pixels.
- Project `overrides` in `naraframe.json` (dotted paths such as `render.palette.accent`) sit on top of the pinned profile. Locked or undeclared paths are validation errors.
- **Trusted recipes** draw a whole scene from local code when the declarative layers cannot carry the choreography. Declare one in `naraframe.json` as `recipes: [{ "id": "<id>", "path": "recipes/<id>" }]`; its directory holds `recipe.json` (`schemaVersion`, `id`, `version`, `entry`, `files`) and the listed `.ts`/`.tsx` files. A scene uses it as `visual: { "type": "recipe", "recipe": "<id>", "params": { ... } }` with empty `beats` and no `camera`; timing is the scene's `durationMs`, audio follows `audioMode` and the project soundtrack. Put episode content (copy, which images, crops, beat times) in `params`; every image is an object with `assetId` naming a ready PNG, and a `crop {x, y, width, height}` in that image's pixels (the file is never edited). Revise copy or framing through `edit` on `scenes.json`, not by editing code. Recipe code may import only `react`, `remotion` and its own listed files, by a quoted relative path that matches exactly one listed file (add the extension when two would match); computed `import()` is refused, and network, clock, randomness, eval or host APIs are refused (`RECIPE_IMPORT_FORBIDDEN`, `RECIPE_CODE_FORBIDDEN`). Rendering bundles a private copy of exactly the listed, hashed files, so an unlisted file in the recipe folder never runs. Recipe `params` that carry brand identity are checked only where `recipe.json` declares them in `bindings`: `[{ "param": "/brand/name", "field": "brand.name" }, …]`, an explicit JSON pointer into the scene's params (no wildcards or expressions) and one of `brand.name`, `brand.cta.label`, `brand.cta.url` or `render.palette.background|surface|text|accent` (the palette after the project's overrides; hex case is ignored). A declared value that differs from the profile, is missing or is not text is a draft warning and blocks production and final (`RECIPE_BINDING_MISMATCH`, `RECIPE_BINDING_PATH_MISSING`, `RECIPE_BINDING_TYPE_INVALID`, `BRAND_FIELD_MISSING`); a duplicated or nested declaration makes the manifest invalid. Bindings are part of the hashed recipe code, so adding, changing or removing them needs the owner's trust again. `RECIPE_BINDING_COVERAGE` (info) and `data.brand.recipes` from `validate --stage production`, `preview` and `render` say how many params are compared and which text params are not: those, and every param of a recipe without bindings, are not brand-checked, so review them by eye before a brand switch. `profile apply <profile> <project> --dry-run` lists each bound param under `plan.bindings.recipeParams` with its current and target value and state (`unchanged`, `changes`, `missing`, `invalid-type`, `field-missing`) and the uncovered params under `recipeCoverage`; change them through `edit`, never by editing the recipe code. Code runs only after the owner accepted that exact code: `RECIPE_NOT_TRUSTED` means ask the owner to review it, and run `pnpm naraframe recipe trust <project> --recipe <id> --authorized-by <name> --json` only when they say so in chat. Any code change needs that acceptance again; `undo` to accepted code does not. Text fit inside a recipe is measured only for slots its `recipe.json` declares in `textSlots`: `[{ "id", "param", "role", "fontSize", "lineHeight", "letterSpacing"?, "fontWeight"?, "box": { "width", "height" }, "maxLines", "wrap": "words" | "none" }]`, all CSS pixels in the 1080×1920 design frame (`lineHeight` is pixels between lines, not a multiplier; `letterSpacing` may be zero or negative). `param` is an explicit JSON pointer to a string or to an array of strings, each element measured on its own (no combined height). The face comes from the profile role after overrides; weight is the slot's, else the role's, else the profile heading weight (display/heading) or body weight (body/label). The recipe receives the resolved style as `props.textSlots[id]` and must draw the text with it, with `white-space: pre-line` for `wrap: "words"` and `pre` for `"none"`. Measurement follows CSS line boxes: `\n` and `\r\n` are one forced break each, a trailing break adds no line but a blank line between breaks counts, and empty text paints no line. In `pre-line` only spaces and tabs collapse and drop at line edges; NBSP and other non-collapsible spaces keep their width, and lines wrap only at spaces (other break opportunities are not modelled, so such text may be refused conservatively). In `pre` nothing collapses or wraps; each line is measured whole, a lone CR as a space. `preview` (540 and 1080, same verdict) and `render` refuse before any frame with `RECIPE_TEXT_OVERFLOW` at the param's path (too many lines, too tall, or a word/line wider than the box); fix the copy through `edit` for the current profile, never by editing the recipe. `validate` cannot measure (no fonts): it reports `RECIPE_TEXT_SLOT_PATH_MISSING` / `RECIPE_TEXT_SLOT_TYPE_INVALID` (warning in drafts, error at production) and `RECIPE_TEXT_FIT_COVERAGE` (info), which names the measured slots and says the rest is not measured. Recipes without `textSlots`, and recipe text outside them, are not checked; collisions and contrast inside a recipe are never checked, so look at the frames yourself and say so.
- `soundtrack` in `naraframe.json`: one `music` track (volume, loop, trimStartMs, fadeInMs, fadeOutMs, optional `duck`) and `sfx` entries anchored to a scene (`sceneId`, `offsetMs`). It never changes video length. Scoped previews carry only their own effects, no music. A planned audio asset is skipped in drafts and blocks final. Two loudness warnings measure the real files: `MUSIC_MASKS_NARRATION` when music under speech is within 6 dB of the voice, `MUSIC_INAUDIBLE` when it is more than 20 dB below. `MUSIC_MAY_MASK_NARRATION` is the cheaper compile-time check on the declared numbers alone.
- `schema` returns a `capabilities` list next to the JSON schemas: the visual forms, layer types, beats, transitions, palette tokens, media formats and audio features this build actually renders, plus what is unsupported and why. Read it before authoring rather than guessing what a scene may contain.
- Vector artwork is supported as `kind: "svg"` in the asset manifest and is placed with an ordinary `image` layer. It is passive data: the loader refuses anything that runs, animates itself, loads another file, or carries a stylesheet, and it scopes the artwork's own ids to the asset. Draw each independently moving part as its own asset.
- A `path` layer is a line the scene can draw and move things along, such as a route or a river. `d` is SVG path data in `viewBox` units, laid onto `frame` without distortion (`PATH_VIEWBOX_ASPECT` when the shapes differ); stroke width and `dash` are viewBox units, so they scale with the plane. A `draw` beat draws it from `from` to `to` (a path with a draw stays hidden until drawn). A `follow` beat moves an ungrouped text, image or shape layer's centre along a path in the same plane, facing its travel with `orient`; when it is the first beat that moves the layer, the layer waits at the path's `from` point before its window (see Poses for later follows). The follower rides the path's declared geometry, so a followed path must keep rotation 0 and have no beats that move, scale or turn it (`FOLLOW_PATH_TRANSFORMED`); drawing and fading it are fine. A path drawn in a zooming world grows with the zoom: draw it after the zoom settles or fade it out.
- A `count` beat counts a number in a text layer without spans (`decimals`, `grouping` `.`/`,`/space, `prefix`, `suffix`). The layer's `text` must be the settled value exactly as formatted (`COUNT_TEXT_MISMATCH`); its text is measured for overflow at each count beat's start and end values; an intermediate value is not measured, so keep intermediates no wider than those endpoints (a count from 0 to 50.000+ is safe, a count through a longer string is not).
- A world group with `billboard: {x, y}` is pinned to that world point but keeps its design size while the camera zooms. Use it for map and street labels. Text in a camera-framed world may sit outside the design canvas; preflight checks it on screen frame by frame.
- With narration, a beat or camera move may carry `at: {phraseId, offsetMs}`: it starts at that measured phrase of the scene's block plus the offset, and `startMs` stays the silent-draft time. Overlaps are checked at the resolved times. Anchor to phrases, never to guessed word timings, and confirm phrase text against the audio before recording `generation.textSha256`.
- A typography role may pin its own `fontFamily` in the profile, which must name a bundled font asset. Measurement and rendering resolve the same face, so a role font is checked, not assumed.
- A scene colour may be a profile slot (`palette.background`, `palette.surface`, `palette.text`, `palette.accent`) in a shape `fill` or a text `color`. Use it whenever the colour belongs to the profile; a literal hex is never repainted by a profile change.
- `PANEL_DEAD_SPACE` warns when a filled backdrop leaves more than 20% of one side empty. Size the panel to what sits on it.
- `CONTRAST_INSUFFICIENT` (warning) measures text, including accent and quiet runs, against the flat colours under it while it is fully shown: the page background and opaque rectangle or circle shapes and their strokes, taking group opacity, reveals and exits into account. A shape counts as the text's backdrop only when its fill, rounded corners included, contains the text box and it is shown for as long as the text. Moving layers are bounded through `transform`, `follow`, `emphasize` (a layer's or its group's) and camera moves; any other movement is not assumed to stay put. Otherwise the check reports `CONTRAST_UNVERIFIED` (info) instead: an image, SVG, path, translucent shape, shadow, a panel that fades while the text is shown, a text box reaching past a curved edge, a `focus` beat or group transform/follow/focus moving a layer, or a layer at another camera depth passing under it. Judge that text in the preview frames, or keep the text box inside an opaque panel's straight edges. The check works on boxes, not glyphs, and neither code proves legibility over artwork.
- `cache clean --dry-run` shows what would be removed; it never touches source, history, receipts, approved or selected builds, or exports.
- Direct edits to the JSON files are still detected and captured as a revision before the next preview or edit; an invalid working copy is reported and left untouched.
